## 2. Décision produit

La plateforme ne doit pas être déclarée prête pour un lancement public complet ni pour des paiements réels avant la résolution des deux P0 suivants : rotation des identifiants administratifs exposés et migration de l’inscription vers une persistance serverless réelle. Les contrôles Moneroo, RLS Supabase et protections des pages administratives sont des gates P1 obligatoires avant l’ouverture commerciale.

## 6. Release gates

Le déploiement est **bloqué** tant que l’inscription échoue, qu’un secret admin reste public, que le webhook Moneroo accepte une signature invalide ou que les données financières restent exposées par des tables sans RLS. Après correction, la validation doit inclure un compte d’essai non privilégié, un rôle recruteur, un créateur WAB, un organizer/jury Awards et une transaction Moneroo sandbox. La production ne doit être déclarée prête qu’après passage de ces scénarios avec logs et preuves de base.

## 7. Non-régression et conservation

Ce PRD ne demande pas de supprimer les modules déjà déployés. Les fonctionnalités existantes doivent être conservées pendant la migration, avec feature flags ou migrations progressives si nécessaire. Les fixtures JSON peuvent être conservés pour les tests locaux, mais doivent être explicitement séparés du chemin de production et interdits dans les handlers serverless.


## 8. Mise à jour Moneroo après test réel

Le flux d’initialisation Moneroo a été validé jusqu’à la création d’un checkout réel de 150 XOF. Le checkout a détecté le Bénin, mais la tentative MTN a échoué côté passerelle avec `GATEWAY_TEMPORARILY_UNAVAILABLE`. La transaction reste donc non confirmée et aucun entitlement ne doit être accordé.

L’exigence produit est désormais la suivante : **EAM ne doit pas imposer une liste fixe de moyens de paiement**. Lorsque `MONEROO_METHODS` n’est pas défini, le champ `methods` est omis du payload ; Moneroo sélectionne alors automatiquement les moyens activés pour le pays et la devise. Pour le Bénin, la liste dynamique Moneroo annonce `celtiis_bj`, `moov_bj` et `mtn_bj`. Une restriction via `MONEROO_METHODS` est réservée aux tests diagnostiques ou à une décision métier explicite.

| Exigence | Statut réel | Critère de reprise |
|---|---|---|
| PAY-02 — Init Moneroo serveur | ✅ Terminé côté code | Vérifier sur Vercel avec les variables `MONEROO_API_KEY` et `MONEROO_WEBHOOK_SECRET` correctes |
| PAY-03 — Webhook signé et idempotent | ✅ Terminé côté code | Déployer puis envoyer un événement signé de test et vérifier 403/200 |
| PAY-04 — Vérification serveur montant/devise/statut | ✅ Terminé côté code | Vérifier un paiement réellement `success` et un paiement `pending/failed` |
| PAY-07 — Sélection automatique des méthodes par pays | ✅ Terminé côté code | Créer un nouveau checkout après déploiement et vérifier les méthodes réellement proposées par Moneroo |
| PAY-08 — Passerelle live disponible | ⚠️ Bloqué fournisseur | Résoudre ou remplacer la passerelle FeexPay temporairement indisponible ; valider Celtiis/Moov/MTN en réel |

## 15. Notifications Web Push — 2026-08-16

Le consentement navigateur est maintenant relié à une souscription Web Push réelle lorsque le navigateur, le service worker et la clé publique VAPID sont disponibles. Le service worker `/sw.js` affiche les notifications et ouvre le lien associé. La route authentifiée `/api/notifications/subscribe` enregistre ou supprime l’abonnement par utilisateur et par endpoint dans `public.push_subscriptions`; la table est protégée par RLS et aucun accès direct `anon` ou `authenticated` n’est accordé.

La paire VAPID a été générée dans un fichier local protégé et non versionné. La mise en production nécessite encore l’ajout des variables `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` et `VAPID_SUBJECT` dans l’environnement Vercel, puis l’application de la migration `20260816_push_subscriptions.sql` dans Supabase. Tant que ces variables ne sont pas présentes, l’autorisation navigateur reste sans erreur mais l’enregistrement serveur est volontairement désactivé.

## 16. Sécurité Supabase — abonnements push et Awards — 2026-08-16

La table `public.push_subscriptions` existait déjà dans le schéma WAB sous la forme `profile_id -> users.id`, `endpoint` et `keys` JSONB. La migration a été corrigée pour réutiliser cette structure sans suppression ni perte de données, puis appliquée avec succès. Une unicité d’endpoint, `updated_at`, l’index utilisateur et le retrait des privilèges `anon`/`authenticated` ont été ajoutés.

L’audit RLS a confirmé que plusieurs tables Jobs, WAB et Awards sont déjà activées en RLS mais ne disposent pas encore de policies métier. Les tables Awards qui étaient encore désactivées ont été verrouillées par la migration `20260816_lock_awards_public_access.sql`. Les policies fines par rôle restent à concevoir avec des tests dédiés ; les routes serveur continuent d’utiliser la service role et ne sont donc pas bloquées par ce verrou.
